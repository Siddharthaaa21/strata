Idempotent Retry Strategy for the Ledger Service
Jul 18, 2026 · Reviewed by Priya

The ledger service currently retries failed writes without an idempotency key, which risks double-charging under network partition. This document captures the recommended approach discussed across three research sessions.

Problem summary

Retries at the gateway layer can duplicate a ledger write if the original request succeeded but the response was lost. We need a deterministic key so replays are safely absorbed.

Proposed key scheme
idempotency_key = hash(account_id, request_ts_bucket, amount)

Keys are stored for 24 hours in the dedup table; a collision returns the original response instead of re-executing the write.
